Rate limiter Ch 4

Step 1
Clarifying questions		 Client-side or server-side? → server-side API
Throttle by IP, user ID, something else? → flexible rules
Scale? → many requests · Distributed? → yes
Separate service or in app code? → your choice · Tell throttled users? → yes
Requirements: accurate, low latency, low memory, distributed, clear exceptions, fault tolerant
Step 2
Core components and API		 Client → rate limiter middleware (or API gateway) → API servers
Counters in Redis (in memory, fast, INCR + EXPIRE)
Pick an algorithm: token bucket, leaking bucket, fixed window, sliding log, sliding counter
Step 3
Deep-dive topics		 Rules (domain, type, unit, requests_per_unit) on disk → workers → cache
Over the limit: 429 + X-Ratelimit-Limit / Remaining / Retry-After, then drop or queue
Race condition → Lua script or sorted set · Sync → centralized Redis, not sticky sessions
Performance → edge servers + eventual consistency · Monitoring → tune rules or algorithm
Key trade-offs Accuracy vs memory (sliding log vs sliding counter)
Allow bursts (token bucket) vs steady rate (leaking bucket)
Strong vs eventual consistency across data centers (exact vs low latency)
Hard vs soft limits · Middleware vs in-app vs API gateway
