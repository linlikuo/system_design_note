System Design Interview by Alex Xu. Summary notes.

The big picture

This is where the chapter ends up. Every section below adds one piece of this diagram.

How the system evolves

1Single server → 2Separate web and DB → 3Load balancer + many web servers → 4DB replication → 5Cache → 6CDN → 7Stateless web tier → 8Multiple data centers → 9Message queue → 10Logging, metrics, automation → 11DB sharding

Each step fixes the bottleneck the previous one left behind.

StepProblem it solves
Separate web and DBWeb traffic and DB load can scale independently
Load balancerOne web server is a SPOF and has limited capacity
DB replicationThe DB is a SPOF and becomes a read bottleneck
CacheRepeated DB reads are slow
CDNStatic files are slow for users far from the servers
Stateless web tierSessions tie users to one server, which blocks autoscaling
Multiple data centersA regional outage, and high latency for users far away
Message queueComponents are tightly coupled, and slow work blocks requests
Logging, metrics, automationA large system can't be run by hand
ShardingThe data grows beyond what one DB server can hold

Key terms

TermMeaning
DNS (Domain Name System)Turns a domain name (api.example.com) into an IP address.
GeoDNSDNS that returns a different IP depending on where the user is, which sends them to the nearest data center.
Load balancerSpreads incoming traffic across a pool of web servers.
SPOF (single point of failure)A component that brings the whole system down when it fails.
ReplicationKeeping copies of the same data on several DB servers.
ShardingSplitting one large DB into smaller parts (shards) on different servers.
TTL (time to live)How long a cached item stays valid before it expires.
StatelessA server that keeps no user data between requests.

Database replication (master / slave)

RoleHandlesHow many
MasterWrites onlyUsually 1
SlaveReads only (a copy of the master's data)Many
BenefitWhy
PerformanceReads run in parallel across the slaves
ReliabilityThe data lives in several places, so losing one server (fire, earthquake) loses no data
High availabilityIf one DB goes offline, another one serves the traffic
FailureWhat happens
A slave goes down (and it was the only one)Reads go to the master until a new slave replaces it
A slave goes down (others remain)Reads move to the healthy slaves, and a new slave replaces the dead one
The master goes downA slave is promoted to master and a new slave is added. The promoted slave's data may be behind, so missing data must be recovered.

Database scaling: sharding

Vertical DB scalingHorizontal DB scaling (sharding)
HowA bigger DB machine (more CPU, RAM, disk)Split the rows across several DB servers by a shard key
LimitHardware limit, SPOF, expensiveAdd more shards as the data grows
ProblemWhat happensFix
Resharding(1) A shard is full because of fast growth. (2) The data is spread unevenly, so some shards fill up first (shard exhaustion).Change the sharding function and move data. Use consistent hashing.
Celebrity / hotspot keyHeavy traffic to one key overloads its shardGive hot keys their own shard, or split them further
JoinsJoins across shards are hardDe-normalize so a query can be answered from one table

De-normalization copies data so a query never has to cross shards.

Cache

A cache tier is a fast, temporary data layer in front of the DB. It improves performance, lowers DB load, and scales on its own.
ConsiderationRule of thumb
When to useData that is read often and changed rarely
ExpirationSet a TTL. Too short means frequent DB reloads; too long means stale data.
ConsistencyKeeping the cache and DB in sync is hard, especially across regions
FailuresA single cache server is a SPOF. Use several cache servers across data centers and overprovision memory as a buffer.
EvictionWhat to remove when the cache is full (see the next table)
Eviction policyRemovesUsage
LRU (least recently used)The item that hasn't been used for the longest timeMost popular
LFU (least frequently used)The item used the fewest timesWhen how often an item is used matters more than when
FIFO (first in, first out)The oldest itemSimple cases

CDN (Content Delivery Network)

A CDN is a set of servers around the world that cache static content (images, video, CSS, JS) close to users.
ConsiderationRule of thumb
CostYou pay for data in and out, so don't put rarely used files on the CDN
Cache expiryTime-sensitive content needs a TTL that is neither too long (stale) nor too short (constant origin reloads)
FallbackIf the CDN is down, clients fetch from the origin
InvalidationUse the vendor's API, or object versioning: image.png?v=2

Stateless web tier

To scale web servers horizontally, move state (such as user sessions) out of them into a shared store: Redis/Memcached, a relational DB, or NoSQL. The book picks NoSQL because it scales easily.
StatefulStateless
RoutingA client must stick to one server (sticky sessions, which add overhead)Any request can go to any server
Adding or removing serversHardEasy, which makes autoscaling possible
Server failureThe user's session is lostNo impact

Multiple data centers

ChallengeSolution
Traffic redirectionGeoDNS sends users to the right DC and handles failover
Data syncReplicate data across DCs so a failover still finds the user's data
Test and deploymentAutomated deploy tools keep every DC consistent

Message queue

A durable buffer for asynchronous work. Producers publish messages, and consumers pick them up and do the work each message describes.
BenefitMeaning
DecouplingA producer can post while the consumer is down, and a consumer can read while the producer is down
Independent scalingAdd more consumers when the queue grows, or remove them when it's short
ReliabilityThe queue holds messages until they are processed

Takeaways: how to scale to millions of users

1. Stateless

Keep the web tier stateless.

2. Redundancy

Build redundancy at every tier.

3. Cache

Cache as much data as you can.

4. Multi-DC

Support multiple data centers.

5. CDN

Host static assets on a CDN.

6. Sharding

Scale the data tier with sharding.

7. Services

Split tiers into individual services.

8. Monitor

Monitor the system and use automation tools.
