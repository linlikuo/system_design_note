Ch 3 — A Framework for System Design Interviews

System Design Interview by Alex Xu. Summary notes.

The 4-step process

StepGoalOutput
1. Understand the problemKnow exactly what to buildAgreed features, scale, and constraints
2. High-level designAgree on a blueprintA box diagram the interviewer has bought into
3. Deep diveGo deep on the most important partsDetailed design of the key components
4. Wrap upShow critical thinking and end strongBottlenecks, improvements, and a recap

The questions are very broad and 45–60 minutes can't cover everything, so time management is essential. The deep dive gets the most time.

Step 1 — Understand the problem and establish design scope

Don't jump into a solution. Ask questions, clarify the requirements, and write down your assumptions.

Questions to ask for any system

AreaQuestions
FeaturesWhat specific features are we building? Which ones matter most?
UsersWho uses it? Mobile, web, or both? How many users (DAU)?
Scale and growthHow fast will it scale up? What scale is expected in 3 months, 6 months, a year?
Tech stackWhat is the company's tech stack? Are there existing services we can reuse?
ConstraintsLatency or availability targets? Consistency needs? Data retention?

Questions to ask for each system

These are starting points. The cheat sheet fills in each system as its chapter is read.

SystemClarifying questions
Rate limiterClient-side or server-side? Throttle by user ID, IP, or something else? How large is the system? Distributed? Should throttled users be told?
Key-value storeHow big is each key-value pair? How much data in total? Is high availability or strong consistency more important? What read and write latency is acceptable?
Unique ID generatorWhat properties must the IDs have: unique, sortable by time, numeric only? How long (e.g. 64-bit)? How many IDs per second?
URL shortenerHow many URLs per day? How short should the URL be? Which characters are allowed? Can URLs be deleted or updated? Are custom aliases needed?
Web crawlerWhat is it for: search indexing, data mining? How many pages per month? What content types: HTML only? How long to store pages? How are duplicate pages handled?
Notification systemWhat types: push, SMS, email? Real-time or can it be delayed? Which devices? What triggers notifications? Can users opt out? How many per day?
News feedMobile, web, or both? Key features: publish posts and see friends' posts? Feed order: chronological or ranked? How many friends per user? DAU? Images and videos?
Chat system1-on-1, group, or both? What is the group size limit? Mobile or web? Online status? Attachments? Message size limit? End-to-end encryption? How long to keep chat history?

Step 2 — Propose high-level design and get buy-in

Build a first blueprint together with the interviewer and ask for feedback. Treat the interviewer as a teammate.
#Key pointWhat to do
1Draw a box diagramShow the key components: clients (mobile/web), APIs, web servers, data stores, cache, CDN, message queue.
2Get buy-inShare the blueprint early and ask for feedback before going deeper.
3Check the numbersDo a back-of-the-envelope estimate (Ch 2) to see whether the blueprint fits the scale. Think out loud, and ask first whether an estimate is needed.
4Walk through use casesWalk through a few concrete use cases to test the design and find edge cases.
5API and DB schema?It depends on the problem. For a huge problem ("design Google search") it's too low-level. For a small one (a multiplayer poker backend) it's fair game. Ask the interviewer.

Step 3 — Design deep dive

By now you've agreed on the goals and scope, drawn the blueprint, and have a sense of what to focus on. Next, work with the interviewer to pick and prioritize the components to go deep on.
Key pointWhat it means
PrioritizeDesign the most critical components first
Follow the interviewerSome interviewers want more high-level design. With senior candidates they often want performance, bottlenecks, and resource estimates.
Go where the problem is hardURL shortener: the hash function. Chat system: low latency and online/offline status.
Manage your timeSkip details that don't matter. For example, explaining Facebook's EdgeRank feed-ranking algorithm in depth uses up time without showing design skill.

Step 4 — Wrap up

🔍 Bottlenecks

Name the bottlenecks and improvements. Never say the design is perfect.

📝 Recap

Give a short recap of the design, especially if you suggested several solutions.

💥 Error cases

Server failure, network loss, and so on.

⚙️ Operations

Monitoring metrics and error logs. How to roll out the system.

📈 Next scale curve

What changes to go from 1M to 10M users?

✨ Refinements

What would you improve with more time?

Dos and don'ts

✅ Dos❌ Don'ts
  • Always ask for clarification. Don't assume your assumption is correct.
  • Understand the requirements. There is no right or best answer: a startup's design differs from one for a company with millions of users.
  • Communicate. Let the interviewer know what you're thinking.
  • Suggest multiple approaches if possible.
  • Agree on the blueprint, then go into detail, starting with the most critical components.
  • Bounce ideas off the interviewer. A good interviewer works with you like a teammate.
  • Never give up.
  • Don't be unprepared for typical questions.
  • Don't jump into a solution before clarifying requirements and assumptions.
  • Don't go too deep on one component early. High-level design first, then drill down.
  • Don't hesitate to ask for hints when stuck.
  • Don't think in silence.
  • Don't assume you're done after giving the design. You're done when the interviewer says so. Ask for feedback early and often.
