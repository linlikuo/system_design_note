Ch 4 — Design a Rate Limiter

System Design Interview by Alex Xu. Summary notes.

What and why

A rate limiter caps how many requests a client can send in a period of time. Requests over the limit are blocked.
BenefitHow
Prevent resource starvation caused by DDoSExcess requests are blocked before they use up server resources
Reduce costFewer servers are needed, and fewer calls go to paid third-party APIs
Prevent server overloadFilters out excess requests from bots or misbehaving users

Step 1 — Understand the problem and establish design scope

Different algorithms have different pros and cons, so first clarify which kind of rate limiter to build.

Clarifying questions

2Throttle by IP, user ID, or something else?Flexible: support different sets of rules
3Scale: startup or big company?A large number of requests
4Distributed environment?Yes
5Separate service or in application code?Your choice
6Tell throttled users?Yes

Requirements

🎯 Accurate

Limit excessive requests accurately.

⚡ Low latency

Must not slow down HTTP response time.

💾 Low memory

Use as little memory as possible.

🌐 Distributed

Shared across multiple servers or processes.

⚠️ Exception handling

Show clear exceptions to throttled users.

🛡️ Fault tolerant

A rate limiter problem (e.g. a cache server going offline) doesn't take down the whole system.

OptionVerdictWhy

Middleware / API gatewayCommonA separate layer that throttles requests before they reach the APIs
Key question to ask yourself: should the rate limiter be on the server side or in a gateway? It depends on the tech stack, the engineering resources, and whether there is already an API gateway (e.g. in a microservice setup).

Algorithms for rate limiting

1Token bucket 2Leaking bucket 3Fixed window counter 4Sliding window log 5Sliding window counter

1. Token bucket used by Amazon, Stripe

A bucket holds tokens. A refiller adds tokens at a fixed rate. Each request takes one token, and if the bucket is empty the request is dropped. Once the bucket is full, extra tokens overflow and are lost.

ParameterMeaning
Bucket sizeThe maximum number of tokens, which is how big a burst can be
Refill rateTokens added per second, which is the long-term rate
How many buckets?Example
One per API endpoint, per user1 post/sec, 150 friend adds/day, 5 likes/sec means 3 buckets per user
One per IP addressThrottle by IP
One global bucketThe whole system allows at most 10,000 requests/sec
✅ Pros❌ Cons
  • Easy to implement
  • Memory efficient
  • Allows short bursts, as long as tokens remain
  • Two parameters (bucket size, refill rate) that are hard to tune

2. Leaking bucket used by Shopify

Requests go into a FIFO queue, and a processor pulls them out at a fixed rate, like water leaking from a bucket. If the queue is full, new requests are dropped.

ParameterMeaning
Bucket sizeThe queue size
Outflow rateHow many requests are processed per second
✅ Pros❌ Cons
  • Memory efficient (the queue has a fixed size)
  • Stable outflow rate, good when a steady processing rate is needed
  • A burst fills the queue with old requests, so newer requests get dropped
  • Two parameters that are hard to tune

3. Fixed window counter

The timeline is split into fixed windows (e.g. one per minute), each with a counter. Each request adds 1 to the counter. Once the counter reaches the limit, new requests are dropped until the next window starts.

✅ Pros❌ Cons
  • Memory efficient
  • Easy to understand
  • Resetting the quota at the end of each window fits some use cases
  • A spike at the window edges can let through up to 2x the limit

4. Sliding window log

Keep a log of request timestamps (e.g. in a Redis sorted set). For each new request:

Example: limit 2 requests per minute
Request atRemoved (older than t - 1 min)Log afterResult
1:00:01none[1:00:01]✅ size 1
1:00:30none[1:00:01, 1:00:30]✅ size 2
1:00:50none[1:00:01, 1:00:30, 1:00:50]❌ size 3 (still logged)
1:01:401:00:01, 1:00:30[1:00:50, 1:01:40]✅ size 2
✅ Pros❌ Cons
  • Very accurate: never more than the limit in any rolling window
  • Uses a lot of memory: even rejected requests' timestamps are stored

5. Sliding window counter hybrid of 3 and 4

Estimate the count in the rolling window from two fixed-window counters. The previous window's count is weighted by how much of it the rolling window still overlaps.

Requests in rolling window = requests in current window + requests in previous window × overlap %
CalculationResult
3 + 5 × 70%6.5, rounded down to 6
6 is under the limit of 7✅ The current request is allowed. The next one hits the limit.
✅ Pros❌ Cons
  • Smooths out spikes, because the rate uses the previous window's average
  • Memory efficient (only 2 counters)
  • An approximation: it assumes the previous window's requests were evenly spread. In practice it's very close: Cloudflare found only 0.003% of 400M requests wrongly allowed or limited.

High-level architecture

Where to store counters? Not in a database (disk is slow). Use an in-memory cache, because it's fast and supports time-based expiration. For example, Redis.
Redis commandUse
INCRAdds 1 to the stored counter
EXPIRESets a timeout on the counter, so it's deleted automatically when the time window ends

Rate limiting rules

Rules are usually written in config files and saved on disk. Each rule defines:

FieldMeaningExample

  - key: message_type

      unit: day
      requests_per_unit: 5

Exceeding the rate limit

SituationResponse
Request is rate limitedReturn HTTP 429 Too Many Requests
Important requests (e.g. orders)Can be put in a message queue and processed later instead of being dropped

Rate limiter HTTP headers

The client learns about its limits from the response headers:

HeaderMeaning
X-Ratelimit-LimitHow many calls the client can make per time window
X-Ratelimit-RemainingHow many requests are still allowed in the current window
X-Ratelimit-Retry-AfterHow many seconds to wait before sending a request that won't be throttled

#Flow

Rate limiter in a distributed environment

Two challenges: race conditions and synchronization.

Challenge 1: race condition

Locks would fix this but make the system much slower. Instead, two approaches are common:

ApproachWhat it isWhy it fixes the race
Lua scriptA small program sent to Redis and run inside RedisRedis runs one script at a time, so read, check, and increment happen atomically and no other request can slip in between.
Sorted setA Redis set whose members are kept ordered by a score. The score is the request timestamp.Each request adds its own entry, so no read-modify-write of a shared counter is needed. Removing old entries by score range gives a sliding window. The commands run together in a MULTI transaction.

Challenge 2: synchronization

With many rate limiter servers, a client's requests can land on different limiters (the web tier is stateless). Each limiter only sees part of the traffic.

Sticky sessionsCentralized data store (Redis)
HowA client always goes to the same rate limiterAll limiters read and write the same counters in one shared Redis
ScalableNo: load can't be spread freelyYes: add limiters freely, since they're stateless
FlexibleNo: a limiter failure affects its clientsYes: any limiter can serve any client
AccuracyEach limiter sees all of its client's trafficEvery limiter sees the full, up-to-date count

Performance optimization

#OptimizationEffect
1Multi-data-center / edge servers around the worldTraffic is automatically routed to the closest edge server, which cuts latency
2Synchronize data with an eventual consistency modelEdges don't wait for each other on every request, so responses stay fast

What is eventual consistency?

Updates are copied to the other replicas asynchronously. For a short time, replicas can hold different (stale) values, but if no new updates arrive, all replicas eventually converge to the same value.
Strong consistencyEventual consistency
ReadsAlways return the latest writeMay briefly return an old value
Write speedSlow: waits for all replicasFast: doesn't wait
AvailabilityLower during network problemsHigher
For a rate limiterExact, but adds latency to every requestGood enough: a few extra requests may get through, and in return latency stays low

Step 4 — Wrap up

🧮 Algorithms

Token bucket, leaking bucket, fixed window, sliding log, sliding counter. See the comparison.

🧱 Hard vs soft

Hard: requests can never exceed the threshold.
Soft: can exceed it for a short period.

📚 Different levels

Rate limit per application (HTTP, layer 7), per IP address (layer 3, e.g. with iptables), and so on.
Hard rate limitingSoft rate limiting
ThresholdNever exceededCan be exceeded briefly
